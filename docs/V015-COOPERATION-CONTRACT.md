# v0.15 cooperation implementation contract

Written before implementation, baseline v0.14.2 `4e104c5`. Product target: [目标提示词](v0.15目标提示词.md). This contract freezes the shared surface; coordinate any changes before editing dependent layers.

## Actions and agreement

One new action type `cooperation`, strict intent-dependent payloads:

- `propose {template_id:camp_meal|scout_and_guard,target_agent_id,role_id,duration_seconds?:300..1800}`; default 900 seconds from creation. Initiator explicitly accepts their own role; invitee must be active and visible within the normal six-tile observation radius. No self-invites.
- `respond {cooperation_id,revision,accept:boolean,role_id?}`; true requires the remaining template role, false forbids role_id. Only the addressed invitee can respond. Invite deadline 150 seconds from creation, capped by the agreement deadline. Neither acceptance nor silence starts an action.
- `confirm {cooperation_id,revision}`; only an already accepted participant, using their current authorized run/epoch.
- `leave {cooperation_id}`; initiator may withdraw before acceptance; either accepted participant can leave later. Does not require revision, so a concurrent review cannot block exit.
- `contribute {cooperation_id,revision}`; camp_meal supplier explicitly commits exactly four turnip (no client quantities).
- `cook {cooperation_id,revision}`; camp_meal cook explicitly performs one atomic two-recipe batch.
- `claim_return {cooperation_id}`; original contributor claims their recorded pending return, no revision required.

`revision` is an agreement/consent epoch, not an action counter. It changes when a new review is required, not for ordinary progress or the first member's confirmation. The second confirmation can therefore use the same observed revision. Action IDs still provide the existing replay protection. Reject irrelevant keys and stale revisions without changing the chosen action.

Two accepted members, one ongoing proposed/accepted agreement per agent. Incoming offers do not count as acceptance; at most two pending incoming offers per target. On accepting one offer, conflicting pending offers can end as unavailable, never reported as a voluntary refusal. No auto-reinvite. Initiator proposal interval at least 60 seconds, persisted; this limits invitations, not ordinary gameplay. Keep at most five nonterminal records and twenty terminal records, and at most one pending return per agent (at most four turnip). Terminal pruning must not lose a pending return. Existing solo gameplay remains usable while returns await capacity.

Store independently of `groups`/legacy `invitations`. States `proposed|active|needs_review|completed|ended`; accepted member records bind role/run/epoch/confirmation. Lifetime is fixed at creation and capped to the two existing authorization deadlines; no extension on acceptance, confirmation, reconnect or restart. Participant run IDs, epochs, invitation target, private rejection details and pending-return balances stay private.

On active participant pause, lease loss, session change, room pause or restart: retain progress/escrow, enter needs_review, invalidate both confirmations once per interruption; each original AI must explicitly confirm. Unaccepted proposals interrupted by these changes end, they do not survive as implicit consent. Revoked/closed grants, explicit leave and expiry end and refund unused escrow. Ordinary work and personal goals are not cancelled by relationship-management actions. Reconfirm does not start work or reopen a paused owner grant. No offline progress.

## Templates and real progress

`camp_meal`: roles `supplier` (供菜者) and `cook` (厨师). Supplier contributes four owned turnip at camp, while idle under existing camp-work checks. Escrow is project-specific. Cook action requires both accepted/confirmed/authorized/active members at safe camp, cook idle, four escrow turnip, cook energy >=4 and room for one turnip_soup in each inventory. Reuse existing two-turnip/one-soup recipe ×2 and four total cook energy. Atomic settlement consumes escrow, grants each exactly one soup, completes project and records actual result. No extra coins/XP. Both private ledgers accurately record changes. Chef's real `cook_item` progress may advance by two; each actual positive food acquisition may count normally. Failed cook is zero change. Remaining escrow on end returns only to contributor; refunds record a ledger entry but never advance collect goals. If capacity prevents refund, persist a bounded pending return; exit still succeeds, explicit claim later is atomic/idempotent. No further new escrow for that agent until their pending return is cleared.

`scout_and_guard`: roles `scout` (侦察员) and `guard` (护卫). Scout first resolves a forest exploration encounter with a non-decline choice while cooperation is active and both consents valid; the discovery must have been found after the cooperation became active. Guard then receives real eligible loot for a forest monster death occurring after that scout resolution. The scout is not credited with damage/loot they did not earn. No same-frame/same-kill requirement, no extra reward. This is sequential patrol, not a claimed shared fight. Use direct successful resolution/reward hooks and unique source IDs, not public event rescanning or inventory balances. No prior kills backfilled. Completing stages records a public joint outcome; no automatic movement, hunt, next goal or follow-up project.

Sources and phase records bounded by this two-stage design. Existing completed real rewards remain after later exit. Transaction rollback includes both members' assets, escrow, progress, ledger and events. Unknown action outcomes follow existing receipt recovery, never resend with a new ID to duplicate a contribution.

## Observation, public schema and UI

`get_rules.cooperation`: versioned limits, template names, role IDs/descriptions, costs/results, durations and example payloads. `observe.cooperation`: nullable current proposed/accepted project, `cooperation_invitations`: at most two addressed pending offers, `cooperation_return`: nullable private pending return. Current project includes exact required revision/role/consent and real shared progress; no teammate balances. Relation management (`respond`, `confirm`, `leave`, `claim_return`, and proposal where legal) remains available during a pending exploration without cancelling it; contribute/cook still obey work restrictions.

Public snapshot: `cooperations` bounded list with strict whitelist: `cooperation_id,revision,template_id,status,created_at,invite_expires_at,expires_at,started_at,ended_at,end_reason,members,progress,escrow,public_result`. Members include accepted IDs/roles and confirmation state only. Never include the unaccepted target/response, run/epoch, owner goals or private returns. Project escrow amount is an explicitly contributed shared fact, not the supplier's inventory. Public ended reason maps refusal/unavailability to `not_formed`; do not publish who rejected. Accepted member departure can be shown without a private explanation. Public event types `cooperation_proposed|cooperation_started|cooperation_progress|cooperation_review|cooperation_completed|cooperation_ended` use the same public whitelist; private invitation/response events only reach authorized participants. No rejected raw payload spread.

Shared shape details: `rules.cooperation.templates[]` has `template_id,name,description,roles:[{role_id,name,description}],steps:[{step_id,role_id,target_count,description}],terms` (concise truthful consent terms). Camp steps are `supply` (supplier, count4) and `cook` (cook, count1 batch); patrol steps are `scout` (scout, count1) and `guard` (guard, count1). Public `members:[{agent_id,role_id,confirmed}]`, `progress:[{step_id,role_id,progress,target_count,completed_at}]`, `escrow:{turnip:number}`; empty escrow is `{turnip:0}`. Public result is nullable `{text,items_by_agent?,completed_at}` with only actual fixed soup distribution; patrol result has no invented items. Source IDs remain private. Public `end_reason` is nullable or `not_formed|withdrawn|expired|member_left|authorization_ended`.

`observe.cooperation` uses this public project shape plus `self_role_id,self_confirmed` (no partner secrets). Incoming `cooperation_invitations[]` shape is `{cooperation_id,revision,template_id,from_agent_id,role_id,invite_expires_at,expires_at}`; terms come from matching catalog. `cooperation_return` is `{cooperation_id,item_id,quantity}`. Server exports `publicCooperation(project)`, `publicCooperations(world)` and `cooperationObservation(world,agent)` so spectator/runtime do not copy private raw state. Public project list sorted recent first. Incoming invites sorted earliest deadline first, deterministic tie break. Public SSE/frame delta must carry the new top-level list.

UI reads server states: one selected-agent summary, collapsible details below map, template roles/actual progress/deadlines/result. Display recently recorded state on disconnection; local expiry only says waiting for server confirmation. Keep existing map/farm boundaries, original appearances, personal goals, life bars and messages. No spectator command controls. Pending targeted invitations/rejection identities must be absent from public HTTP/SSE, not merely hidden in React.
